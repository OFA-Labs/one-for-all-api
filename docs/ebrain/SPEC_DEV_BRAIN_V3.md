## 0. Executive decision and reading guide

V2 correctly identified the central architecture: immutable source evidence, compiled fact cards, hybrid retrieval, deterministic currency resolution, asynchronous maintenance and answer assembly. V3 retains all six responsibilities. It adds the missing contracts that make those responsibilities safe when 100–200 developers and their agents write concurrently.

**Core invariant:** a source record proves that a claim was made, not that the claim is true. A fact card is a disposable projection, not an authority. An authorized, versioned adjudication policy operating on accepted evidence and explicit identity decisions determines which claim is current. Search is a candidate discovery mechanism; it cannot confer authority. When evidence is insufficient, the correct state is uncertainty, not a guessed value.

The 30 findings in §3 are individually mapped to mandatory design controls and release tests. Sections 4–20 are the normative replacement design. Sections 21–26 cover proof, migration, rollout, acceptance and unresolved owner decisions. Source citations such as `V2 §9.3, lines 167–170` refer to the supplied Markdown file, not to separately inspected repository files. All new architectural choices and targets are proposals unless explicitly identified as V2-reported evidence.

## 1. Purpose, boundaries and success conditions

### 1.1 Product scope (preserved)

A shared engineering knowledge service for 100–200 developers, with a target of 50,000–100,000+ distinct facts and a separately sized event history. Clients include OFA voice, Claude Code, Codex, OpenCode and authorized HTTP/MCP clients. The brain helps agents use actual engineering decisions rather than repeatedly rediscover context.

In scope: specs, ADRs, decisions and rationale, approved configuration, API contracts, runbooks, dependency notes, code facts, incident summaries, task conclusions, reviewed knowledge derived from documents, and sanitized untrusted external evidence. Preserve repository/branch/environment qualifiers. Out of scope: HR data, personal profiles or notes, customer PII, credentials, raw permanent chat/meeting archives, payment/CRM analytics, and autonomous authoritative self-healing. A developer-only workspace or single-user mode is allowed for engineering content, not personal knowledge. Identity and access audit metadata are necessary operational data, separately controlled and minimized; they are not searchable memory facts.

Priority order: security and authorized correctness (hard constraints), reliable current-value selection and completeness, query performance, then operational cost. No token-efficiency requirement for the accuracy-first mode; compact voice and agent bundles remain optional. Do not weaken safety to reach a numerical accuracy or latency target.

### 1.2 What can actually be promised

The service cannot know the external world's newest true value without trustworthy and timely evidence. In a synthetic harness the oracle supplies ground truth; in production the service returns the latest authorized, supported assertion for the requested scope/time, or an explicit uncertainty/conflict state. It must distinguish a **decision** (what should be true) from an **observation** (what is currently observed in a specific deployed environment). Do not silently turn intended state into observed state.

A current result MUST have exactly one resolved value for a scalar fact, or the complete resolved set for a fact explicitly defined as multi-valued. No invalid, superseded, unauthorized, unresolved, deleted or derived-only value may be labelled current. A valid answer must be scoped, sourced and snapshot-consistent. Security is a release gate; measured zero leakage is not proof that leakage is impossible.

## 4. Domain model and data contracts

### 4.1 Vocabulary and identity boundaries

- **Event:** immutable sanitized record of an attempted accepted domain assertion or control action, identified by `(org_id, op_id)`. Acceptance means durable receipt, not necessarily authoritative application. Rejected requests get minimal security audit metadata, not a durable raw content event.
- **Fact:** one typed engineering predicate about a resource in a precise scope; `fact_id` is stable and opaque. A value change is a new claim/revision, not a new fact. A source document may contain multiple facts; split into separate assertions linked to one source snapshot.
- **Claim:** typed value (or tombstone) about a fact, with authority, provenance and effective interval. `value_code` is a server-assigned opaque stable identifier for a claim/version; legacy codes are scoped aliases, never authority or globally unique by assumption.
- **Identity binding:** auditable association of a claim to a fact, determined independently of the card. **Card:** cache of approved identity bindings and resolved status at a known ledger/policy watermark.
- **Snapshot:** `(org_id, knowledge_seq, valid_at, identity_generation, policy_version, auth_epoch)` plus active retrieval generations. All state in a response is consistent with this cut; current authorization applies even when reading history.
- **Scope:** organization plus engineering workspace/team/project and audience grant. Project is a stable ID, not user-provided name. Organization-wide facts are explicit, never wildcard inferred from missing project. Individual developer workspace is a restricted engineering project, not a personal diary.
- **Claim kind:** `decision`, `observed`, `recommendation`, `derived`, `external_evidence`. Only authorized `decision` or admissible `observed` claims may establish current state; the two kinds are separate predicates or explicit facets. `recommendation`, `derived`, and `external_evidence` never become current merely by repetition.

### 4.2 Typed canonical key and value schema (C02, H09)

Proposed canonical key: `(org_id, scope_id, resource_namespace, resource_id, predicate_id, claim_kind, qualifiers_normalized)`. Qualifiers may include repo ID, component, branch/ref, deployment environment, API version, token type, region or platform. Predicate registry declares required/optional qualifiers, cardinality, type, normalization, permitted writers, source classes, freshness policy and whether valid intervals are allowed. Unknown required qualifiers are an explicit `unknown` state and cannot equal production/default automatically. Do not stem away meaningful distinctions (`access`, `refresh`, `approval`, `prod`, `stage`). Stable resource IDs survive renames; path aliases are time-bounded.

Example: `org=A / scope=payments / resource=auth-service / predicate=token.ttl / kind=decision / token=access / env=prod / branch=main`. Canonical value `{"type":"duration","seconds":1800,"display":"30 minutes"}`. Refresh token, staging, actual observed prod TTL and another project's identical path remain separate. Scalar values use strict types, precision and units; JSON schemas restrict fields, collections and length. Unit conversion must use deterministic exact normalization where possible. String free text is evidence, not a substitute for a typed scalar; ambiguous conversions are reviewed. Multi-valued predicates explicitly define set membership add/remove semantics, stable element IDs, and conflict resolution; absent support in v1 implementation, reject them as unsupported rather than treating sets as scalars.

### 4.3 Source registry and evidence contract (M06, M10)

Every source has `(org_id, source_id, owner_scope, kind, trust_contract_version, allowed_predicates, connector_identity, status)`. Every sanitized snapshot has immutable ID, stable upstream revision/commit/ETag when available, ingestion sequence, content digest, source path, parser version, ACL lineage, sanitized bytes or object reference and normalized offset mapping. A citation points to snapshot ID + span (byte offsets and optional line numbers) + span digest; original location is display metadata. Verify offsets and digest against the exact sanitized revision, never the mutable live URL. If raw object is erased, mark citation unavailable and re-evaluate dependent claims. Redaction must happen before durable storage; never retain a hidden unredacted copy for convenience.

A connector is read-only unless separately authorized. Poll/checkpoint by source revision, deduplicate identical snapshots within their scope, handle rename through stable IDs. Mark incomplete scans and do not infer deletion from a missing page, permission error or partial checkout. A confirmed deletion/retraction appends a source-status event; it does not automatically tombstone an approved decision unless its predicate/source contract explicitly defines that dependency. A document extraction emits candidate assertions with source spans; source authority does not transfer to an LLM-generated paraphrase. Meeting material is opt-in, sanitized, processed ephemerally within bounded sessions, and only reviewed durable conclusions with evidence references are retained; do not promise permanent verbatim transcript citations when transcripts are intentionally not retained. A reviewed conclusion becomes its own signed/approved source artifact.

## 5. Security principal, scope and authority (C01, C04, C09)

### 5.1 Identity and grants

Use OIDC SSO (Google Workspace/Microsoft Entra or owner-approved provider) and SCIM where available. Validate issuer, audience, signature, expiration, nonce/state where applicable, and organization membership; map immutable issuer+subject to an internal opaque principal ID. Do not trust email domain, display name or token-supplied arbitrary org IDs as proof of membership. SCIM provisioning creates/revokes membership, not historical claims. Agent/service credentials are short-lived or rotation-managed, audience-restricted, scoped to a human or service owner, resource, action, expiry and delegation ID. The server derives actor, org, role, authority, source identity and grants from authenticated context; clients cannot set them. Separate service accounts for API, workers, migration, backups and audit. Runtime database roles are neither owners nor superusers and have no `BYPASSRLS`.

Actions: `read_current`, `read_history`, `write_assertion`, `write_observation`, `propose`, `approve_identity`, `decide`, `promote`, `manage_source`, `maintain`, `read_audit`, `erase`, `recover`. Explicit deny overrides allow. A grant includes scope, predicate/domain, allowed claim kinds, role, action, validity and delegation limits. A missing, empty, invalid or expired grant returns deny. Scope hierarchy grants are explicit; no automatic sibling visibility. Organization policies may be readable by all members without granting mutation rights. Project/private engineering notes cannot flow upward without reviewed promotion. Org-wide alias vocabulary may contain only approved non-sensitive terminology; it must not expose hidden card existence or content.

### 5.2 Authority is not an integer supplied by a writer

Within a predicate's domain, default proposed precedence for decision assertions: authorized org/domain decision owner > designated domain verifier > member assertion > agent inference > external. Org role alone does not grant technical authority outside domain. Observations use a separate trusted-source contract (e.g., signed deployment metadata) and cannot overwrite intended policy. Agent can execute an expressly delegated decision only if grant explicitly authorizes that predicate, scope, action, effective range, and authority ceiling. `supersedes`, `base_op`, confidence, source tier and model outputs are references or evidence, never permissions. Non-authorized writes may remain non-current proposals/evidence; denied mutation requests do not masquerade as valid decisions.

For decision mutations, authorization is validated at transaction commit, with the grant and policy revision recorded as historical evidence. Current access is checked on every query; revoking a contributor's login does not erase legitimate earlier decisions. A grant compromised in the past requires explicit investigated invalidation/correction of affected events. High-risk operations (cross-scope promotion, existing-fact merge/split, destructive correction, policy changes and erasure) require independent authorized approval; no self-approval by the proposer. For single-user development, bootstrap owner may approve explicitly in isolated mode, audit exception, never use it in company mode. If organization lacks two eligible reviewers, high-risk action is blocked until owner establishes a reviewed exception policy; not auto-approved.

### 5.3 Authorization enforcement

Composite tenant and scope foreign keys, RLS `FORCE ROW LEVEL SECURITY` on all tenant-owned tables, `USING` and `WITH CHECK` policies, and request-local trusted context in transactions. Include grant intersection on joins, links, source spans, history, projections, proposals, receipts and counts. Transaction pooling must clear context; no raw caller SQL or unrestricted SECURITY DEFINER RPC. If a privileged maintenance procedure is unavoidable, pin search path, validate caller/scope and audit. Separate public control-plane model metadata from tenant-owned calibration. Cache keys include org, effective scope/grant fingerprint, auth epoch, query cut, policy and generation; never reuse a broader view for a narrower one. Do not expose hidden existence via different 403/404 bodies, result counts, ranking, debug, autocomplete, timing where practical, or global aggregate access. §11 describes remaining boundary details.

## 6. Fact registry, filing and safe identity evolution (C02, C08, H02)

### 6.1 Identity is an explicit ledger, not a cluster output

Create append-only identity events `REGISTER_FACT`, `BIND_CLAIM`, `UNBIND_CORRECTION`, `ADD_ALIAS`, `RETIRE_ALIAS`, `MERGE_FACTS`, `SPLIT_FACT`, `REKEY`, each with actor, scope, evidence, valid/recorded cut, prior generation and approval when required. Every applied claim belongs to exactly one active fact at a given identity cut. Unassigned claims are durable pending evidence, not independent current cards. Old fact IDs remain redirect/history handles with authorized visibility, and historical queries use the identity mapping as known then. IDs are never reused. Keep explicit mappings from legacy code/op to canonical IDs.

Filing sequence:

1. Validate scope, claim kind and predicate schema. If an authenticated structured `fact_id` or lineage target is provided, resolve exact authorized fact; validate all qualifiers and source compatibility. A mismatch is rejected or review-pending, never overridden by fuzzy score.
2. If full canonical key is known, perform atomic unique lookup/register. An authorized structured new fact may be created directly; use unique constraint to prevent duplicate registration. For a legacy ambiguous phrase, use approved alias lookup within the exact scope/qualifiers; aliases can map to multiple facts and require disambiguation.
3. For unresolved text, classifier returns strict schema `candidate_fact_ids[]`, `candidate_new_key`, `confidence`, `near_miss_ids[]`, `evidence_span_ids[]`, `missing_qualifiers[]`, `reason_codes`, `model_manifest_id`. It receives only authorized sanitized context, cannot write identity or call tools. Validate all IDs, types and anchors server-side. LLM may help propose a parse/filing candidate; it never decides authority/current. No assumed 90% automatic coverage; measure it.
4. Apply deterministic binding if a unique authorized exact registry match is proven by required typed evidence (including qualifier compatibility). Similarity-only candidate, novel predicate, missing qualifier or conflicting anchors -> pending review or request clarification. A high calibrated score prioritizes review, not a license to merge two existing facts. New fuzzy aliases may be suggested; approve explicitly if they introduce a new identity equivalence. Existing approved aliases may be used deterministically. Preserve source event before invoking models as in §7.
5. Record decision with reason and generation, then materialize cards. For ambiguous unassigned evidence that could modify a known fact, install a pending impact fence (§7.4) before acknowledging; absence of binding is not proof the old value is safe.

### 6.2 Merge / split protocol

Review proposal includes all affected fact IDs, bindings, qualifiers, value timelines, evidence spans, proposed remapping, before/after resolver states, impacted scopes and generation. Merge only if same canonical semantic predicate and authorization boundary, or explicit approved normalization of duplicate keys; cross-project similar facts remain scoped variants under a non-authoritative family relation. Do not use transitive similarity (`A≈B`, `B≈C`) as equality. Split assigns each claim to exactly one new/existing fact or leaves it pending, never copies it as authoritative to both. Run deterministic conflict checks, re-evaluate quota and invalidate affected caches/indexes atomically at activation. Historical state retained. Approve via §14. Rebuild materializes from ledger and identity decisions, not from a fresh nondeterministic classifier pass. Independent labelled probes detect consistent but incorrect identity decisions; rebuild-and-diff alone cannot.

### 6.3 Calibration and review

Construct disjoint training/calibration/test sets of real sanitized and synthetic alias pairs, hard negatives (same terminology/different qualifier), out-of-domain, long tail, Unicode, units and renamed resources; split by fact family/repository, not randomly duplicated paraphrases. Per model/preprocessing/locale/domain, estimate precision-recall, coverage, reliability and uncertainty; choose thresholds against cost of over-merge and fragmentation. Thresholds are deployment-config proposals, not universal cosine .95. Shadow mode cannot mutate production, and reviewers see evidence rather than raw score alone. Report false merge, false split, pending rate and review latency separately. Drift/low sample stratum => disable automatic heuristic filing, keep exact rules; evaluate reviewer outcomes before activating changes.

## 7. Storage, ingestion and consistency protocol (C03, C05, C06, H10, M10)

### 7.1 Persistence layout

PostgreSQL is the proposed production transaction boundary from the first multi-user release; pgvector and PostgreSQL full-text search are accelerators, not truth stores. PGLite/SQLite may remain a single-user development adapter with explicit capability differences; do not claim their tests establish production RLS/concurrency. Object storage is optional for large sanitized snapshots. All tenant tables include `org_id` in primary/foreign keys; all content tables have a scope or inherit it via an enforced composite FK. Use UTC `timestamptz`, integer ledger sequence, schema versions, non-null tenant identifiers and explicit enum constraints. Do not let arrays of unchecked IDs substitute for relationship tables.

### 7.2 Transaction and sequence

For initial team sizing, serialize state-changing commits per organization using a locked organization state row, incrementing a transactionally stored commit counter (not a standalone sequence that can allocate out of commit order). This is a simple correctness baseline; benchmark contention before optimizing. All identity, decision, authorization epoch and ledger transitions that affect snapshots participate in this ordering. Do not hold this lock during model calls, network calls or object upload. Object staging uses sanitized encrypted content, content hash, durable object confirmation before committing references; orphan cleanup is idempotent. If switching to finer-grained locks, prove equivalent cut semantics and use stable lock ordering.

Within the transaction: validate current grant and policy, reserve quota, check idempotency, insert event/claim, apply only deterministic admitted transitions, create pending-impact record if necessary, append outbox, update authoritative watermark/counters, commit. Never acknowledge before commit. Workers consume outbox at least once using a stable job key `(org_id,op_id,job_type,generation)` and transactional upserts of projections; no exactly-once delivery assumption. A durable applied marker and watermark advance only after all required work for that sequence is completed or explicitly classified pending/terminal; pending fences are separate and cannot be skipped by watermark advancement. Retry with bounded backoff; dead-letter queue requires review; preserve safe read state. A later identity review is itself a new commit, not a rewrite of earlier event.

### 7.3 Ingestion and response states

1. Authenticate, authorize scope/action, bound request sizes, parse strict schema, validate source contract, reject unsupported input and sanitize before logging/persistence. Gate errors fail closed; model availability is not a security gate.
2. Normalize typed fields and fingerprint the sanitized request including fact/scope, valid interval, base and source revision. Idempotency key scoped to org, endpoint, principal and request semantics; same key and digest yields original receipt subject to current authorization, different digest yields conflict. `op_id` uniqueness is separately enforced; never overwrite an existing event. Preserve authorized rejected-transition evidence only if safe and policy allows; otherwise minimal audit.
3. For exact admitted identity and authorized assertion, resolve in the transaction or mark durable replay work; for unassigned free text, append sanitized claim and fence relevant possible facts. Source payload is retained even if classifier down, but only after security checks.
4. Response distinguishes `accepted_pending`, `applied`, `accepted_noncurrent`, `conflict`, `rejected`; `202` for pending, `201` for new committed applied/noncurrent result; idempotent replay `200` with original receipt plus optional current processing state. `applied` means the authoritative transition exists, not that all search accelerators have caught up. Every accepted receipt has op ID, commit sequence, status and processing-status URL. Do not report a write as applied if only a job was queued.

### 7.4 Read-after-write and pending-impact fence

A query chooses a primary-database read snapshot containing the latest authorized ledger cut at its start (or a caller-supplied minimum receipt sequence). Within it, use cards/indexes only as hints. For each candidate read authoritative claims and identity/decision state at the cut, including newly committed unindexed claims. Maintain a small authoritative exact registry and pending-impact index updated synchronously; supplement retrieval with delta search for admitted facts newer than active index watermarks. If a pending unassigned claim may change a candidate's state, mark the result `pending_verification` without any current value unless a deterministic check proves it cannot affect that fact. If identity is wholly unknown, conservatively fence the relevant scope/domain; if even scope/domain is unknown, reject or keep in authorized evidence-only intake with no assertion status. An untrusted, non-authoritative or incapable assertion cannot fence a valid higher-authority fact simply by mentioning it; rate-limit eligible pending claims. Large pending set: return explicit incomplete/pending and backpressure; never falsely assert freshness. Remove fences only in committed classification/decision transition. A query that began before a write may legitimately return its earlier snapshot; disclose snapshot and allow `min_seq`. A replica is eligible only when it can serve the required committed cut and current authorization; otherwise use primary or return unavailable. See §10 for final authorization fence.

### 7.5 Temporal contract (C05)

`valid_from`/`valid_to` are real-world effective times, half-open `[from,to)` where `to=null` means open. `recorded_at` and `commit_seq` are server-assigned knowledge times; client clocks are metadata only. A retroactive correction is an authorized explicit event referring to affected claims and valid interval; never backdate recorded time. Future-effective decisions are scheduled, not current before `valid_from`. Unknown legacy effective time remains unknown (do not invent); use a labelled recorded-time approximation only if query explicitly opts in. Use one snapshot for all response items. Query forms:

- `current`: effective time = server query time, knowledge cut = current committed seq.
- `as_of_valid(t)`: what currently accepted evidence says was effective at t (latest knowledge cut).
- `as_known_at(t)`: only events committed/known by t, effective time defaults to t; expose corresponding sequence. If timestamps tie use `knowledge_seq` for exact replay.
- `bitemporal(valid_at=t, knowledge_seq=s)`: explicit both; identity, source status and semantic policy version as known at s, subject to current access and erasure restrictions.

Historical authorization never restores access. If a source/identity correction is known later, it does not alter earlier knowledge cuts. Rule updates are immutable policy events and require explicit effective scope; new policy does not silently change past knowledge. Exact historical answer means authoritative state at that cut, not identical natural-language wording or previous ranking. Preserve original query receipt to reproduce what was actually sent.

## 8. Deterministic currency resolver (C01, C05, C06, C10, H09, M08)

### 8.1 Inputs and rule ordering

Inputs: canonical fact ID, explicit scope, knowledge cut, effective time, approved identity bindings, claims/source status, authorized decision ledger, predicate schema and versioned policy. No model output, similarity, card current field, rerank score or usage feedback is allowed as a deciding input. Use a pure state-machine implementation with a reference interpreter in tests. Resolve decision and observed predicates independently; show discrepancies without rewriting either.

Preserve T1–T7 names from V2; their exact legacy implementation was not supplied, so planner MUST reconcile compatibility in an ADR and test old behavior against the proposed rules. Normative precedence: validate identity/authorization and source eligibility first; explicit approved resolution/correction and lifecycle transitions second; branch/base consistency and conflict handling next; effective-time and authorized revision ordering last. A newer timestamp alone is never sufficient to override another authority or a conflict.

| Rule | Proposed precise behavior |
|---|---|
| T1 recency | Among eligible comparable revisions of the same fact, choose by explicit lineage and effective interval; if an authoritative source contract defines monotonic revision or direct sequential assertions, use its verified ordering. Equal or incomparable contradictory claims are not ordered by UUID, arbitrary timestamp or model score. |
| T2 authority | Evaluate grant at commit and authorized predicate/domain. Lower cannot override higher via `supersedes`; explicit bounded delegation or an approved decision is required. Higher-authority valid transition can resolve lower competing proposals if it references the affected branch/base or an explicit decision scope. |
| T3 external | External/untrusted/injection-flagged inadmissible data is evidence only; only a separately approved first-party decision or authorized observation creates an eligible claim. Flags cannot be cleared by model. |
| T4 conflict | Distinct eligible equal-precedence competing values from a shared observed base or overlapping interval with no approved ordering are unresolved; no scalar current in affected interval. Duplicate equivalent normalized values are corroboration, not conflict. |
| T5 base | Referenced base must belong to same fact/scope and be the expected head at writer's observed cut. Reject unrelated/cyclic/invalid bases. Known stale write without valid competing-branch evidence is rejected or noncurrent; do not silently rebase. |
| T6 lifecycle | Authorized explicit tombstone terminates state in its effective interval and prevents implicit resurrection. Only explicit authorized `RESTORE_FACT`/new lifecycle decision may reactivate; missing document alone is not a tombstone. |
| T7 derived | Summaries, recommendations, model-generated claims and external evidence cannot supersede primary state; explicit separately sourced authorized approval creates a new decision, not a mutation of derived evidence. |

`supersedes` references must be same fact and compatible scope, target existing known prior claim(s), form an acyclic graph, and be granted as a transition. `expected_head` plus `observed_seq` are required for normal structured mutations to an existing decision except preapproved source contracts. Source replay uses source monotonic revisions, dedup and effective intervals, never a user-supplied clock alone. A direct authorized sequential assertion with no explicit lineage is allowed only if the predicate/source contract permits it, the fact key is unambiguous, and the server records the observed/accepted head and generated revision edge under lock. For ambiguous free-text without ordering or authority evidence, queue review; V2's expectation that every silent update becomes head cannot be safely guaranteed. Measure the resulting coverage/accuracy trade-off explicitly.

### 8.2 State transitions and conflicts

State at a cut/time is one of `absent`, `current`, `conflict`, `withdrawn`, `pending_verification`, `unknown` (including unsupported/erased evidence), with per-claim annotations `current`, `historical`, `superseded`, `conflict`, `noncurrent`, `untrusted`, `derived`, `scheduled`, `rejected`, `withdrawn`. A stale observation has `unknown`/last-known display, not current if freshness contract expired. An unresolved conflicting scalar has zero current claims. Equivalent corroborating scalar assertions produce one current value code with supporting evidence; define a stable representative (approved primary claim, or first admitted equivalent claim) and expose equivalent codes separately, not multiple current alternatives. A semantic version change creates a new claim ID/code; a repeated identical observation need not create new fact capacity. Multi-valued semantics follow §4.2.

Concurrent example: initial 45m at seq 100; two equally authorized writers both observed seq 100 and propose 30m/60m. First commits seq 101; second submits base+observed cut, verified as a competing authorized branch; append conflict at seq 102 rather than choosing by millisecond. Until approved resolution, no current in overlapping effective interval. If second observed seq 101 but still references old 45m, it is a stale-base attempt, not a legitimate concurrent branch. If an unauthorized agent proposes 90m, it is noncurrent/rejected; it cannot manufacture a conflict that masks the human head. All transitions use the organization commit fence and record reasons. A resolution references conflict ID, competing branches, chosen/new value and rationale, authorized decider and base generation; new concurrent branch invalidates an old resolution proposal until re-reviewed. Effective interval segmentation handles corrections/future scheduling; replay must include overlapping boundaries and avoid treating a historical revision as an active contradiction.

### 8.3 Resolver outline (pseudocode contract)

```text
resolve(fact, cut):
    bindings = identity_as_known(fact, cut.knowledge_seq)
    policy = policy_as_known(cut.knowledge_seq, fact.scope)
    claims = load_bound_claims_and_control_events(bindings, cut.knowledge_seq)
    eligible = check_admission_authority_source_and_lifecycle(claims, policy)
    intervals = deterministic_reduce(eligible, approved_decisions, policy)
    result = interval_at(intervals, cut.valid_at)
    if relevant_authoritative_pending_or_evidence_missing(result, cut):
        return pending_or_unknown_without_current(result)
    return assert_cardinality_and_attach_evidence(result)
```

The reducer is deterministic given identical inputs, may use validated checkpoints keyed by ledger/policy/identity cut, and must agree with full reference replay. Every status has reason codes; `contradicted_by` is a typed link only between relevant incompatible claims with valid-time context, not between unrelated or merely older values. Exact query of a superseded code returns it labelled historical and, if permitted, the current replacement separately. Do not force history into current search results.

### 8.4 Read history, logical rollback and disaster recovery are different

`as_of` is read-only. Logical rollback is an authorized compensating decision referencing the target historical state, current head/conflict and reason; it creates a new event/code and preserves intervening history. If target is erased, invalid, inaccessible or no longer applicable, reject or request new evidence. Multi-fact rollback uses reviewed impact manifest and atomic transaction or explicitly documented staged operation; no half-applied batch advertised as complete. Disaster recovery restores system infrastructure (§17), not a user's desired historical state. Test these three semantics separately; V2's `rollback_exact=1` is retained as a strict target for well-defined authorized logical rollback and replay oracle cases, not a promise of replaying prohibited content.

## 9. Compiled projections, evidence and consolidation (C08, H04, M05, M06)

A card is disposable: `fact_id`, canonical label, approved aliases, qualifiers, state and optional cached current code, timeline pointer, conflict references, related links, field evidence, projection generation, ledger/identity/policy cut, model manifest, updated timestamp. Card tables are not directly writable by clients. A deterministic materializer builds them from the ledger and approved identity mappings. Every factual field has claim/source IDs and spans, or explicit system-derived reason; generated prose is separate. Source verification checks exact sanitized revision and span digest, typed subject/value/unit/negation where structured evidence permits. String presence alone is not semantic entailment. For free-form evidence, unsupported or ambiguous extraction stays unverified pending review; NLI/LLM cannot certify its own text.

Run incremental materialization plus scheduled full rebuild into a shadow generation. Compare canonical state digest, identity assignments, source coverage, current codes, conflicts, pending fences and scope invariants against production at identical cut. Independently compare to a simple reference replay and labelled identity samples; same bad approved identity can pass both materializers and needs semantic review. If divergence affects current correctness, fence/disable the projection immediately and fall back to authoritative replay; this is an automatic technical safety action, not authoritative demotion or deletion. Swap generation only after reconciliation, tests and approval when semantic config changes. Do not silently overwrite a card by a fresh model interpretation.

Dream cycle jobs: propose alias/identity changes using §6, typed contradictions (same fact, overlapping effective interval, different normalized values), then advisory NLI for unstructured cases after subject/scope/time gate. NLI may miss real conflicts; monitor sampled false negatives and false positives. Lint: missing/corrupt citations, orphan domain ownership, unbound claims, duplicate keys, stale observations, broken links, invalid authority references, pending-fence age, projection watermark, unresolved proposals and erased-source dependencies. Stable issue ID from target+rule+evidence revision deduplicates repeated reports. No autonomous merge, authoritative demotion, delete or conflict resolution. Deterministic invalid-state detection may suppress unsafe current badges; owner review changes authoritative state. Refresh only changed search documents, invalidate affected graph/cache and retain versioned generation manifest. Ranking feedback is advisory: authenticated, bounded, offline evaluated, human-approved, never changes authorization, identity, evidence or replay. Audit each activation; rollback config if recall drops.

## 10. Query, retrieval and answer correctness (C03, C04, H01, H10)

### 10.1 Request interpretation and candidate generation

Validate query scope and target kind, optional qualified fact ID/path/code, as-of mode and requested completeness. Structured lookup takes precedence over semantic query. For natural language, produce typed query facets and qualifier candidates; parser/model is advisory, missing scope/qualifier remains unknown. Multiple possible authorized meanings must be exposed or clarified, not collapsed. Never map a missing environment to production without a documented explicit default visible in the answer. Scope before each retrieval branch, including graph traversal and exact history lookup. Use registry exact lookup (fact ID/full key/approved alias), qualified source/path/code matches, lexical FTS ranking (PostgreSQL `ts_rank`/`ts_rank_cd` is not BM25; use tested BM25 extension/service only if explicitly adopted), vector search with compatible manifest, and scoped graph expansion. Graph near-miss edges are disambiguation candidates, not equality. Raw unassigned delta evidence is searched as pending, not current.

Keep a union of protected exact candidates and deterministic qualifying matches outside reranker truncation. Use separate branch budgets and retain branch-level rank provenance. RRF proposed formula `sum_i w_i/(k0+rank_i)` with fixed positive approved parameters; rank starts at 1, absent candidate contributes zero. Normalize reranker scores using held-out calibration; cannot drop protected candidates. For filtered ANN, evaluate recall against exact scoped scan; if candidate coverage is poor, increase search effort, use iterative scan where supported, or exact filtered fallback. Never broaden authorization to improve recall. A global ANN graph may affect timing/recall even with post-filtering; benchmark and isolate by security domain where needed (§11).

### 10.2 Adaptive shortlist and verification

Start from calibrated branch pools. Widen if any required facet missing, protected candidate unresolved, close score gaps/high uncertainty, low branch agreement, incomplete index coverage, possible near-miss or ambiguous subject. Score gap/entropy is heuristic, not proof of completeness; use minimum and maximum budgets measured by domain and workload, iterative expansion and exact/lexical fallback. If max budget reached, return `partial` or `needs_clarification` rather than fabricate completeness. Deterministic verification checks known typed qualifiers, exact identity, source/admission compatibility and scope; it cannot prove arbitrary natural-language paraphrase equivalence, so ambiguous interpretations remain explicit. Verify each candidate and requested facet, not merely whether at least one verifies. Re-resolve all admitted candidates from authoritative state at snapshot cut. Multiple valid facts in an ambiguous query are grouped and labelled separately. A historical code match is not promoted to current. Current appears before historical claims within each fact, not before another relevant fact simply because current.

### 10.3 Response status and final authorization

Return separate `answer_status` (`complete`, `partial`, `ambiguous`, `pending`, `not_found`, `unavailable`), per-fact state, retrieval confidence (calibrated, optional), source freshness, snapshot and degradation flags. `not_found` means no authorized match within declared complete search contract, not proof no hidden fact exists; free-text unknown can be incomplete. Confidence cannot override a conflict or pending fence. Include source evidence IDs and permitted excerpts, reason codes, lineage and current/history distinction. Budget clipping never drops status, conflicts or required evidence without marking incompleteness. For exact current queries with requested minimum receipt, wait bounded duration for snapshot or return pending/unavailable; never silently serve earlier cut. For natural-language query, incomplete index watermark requires delta overlay or labelled degradation. If model/reranker/vector unavailable, run eligible remaining arms and downgrade completeness; exact replay remains valid if identity and authorization proven.

Immediately before serialization/delivery, revalidate current auth epoch and grants on every result, source, link, trace and citation. If epoch changed, re-run or fail closed rather than serving stale permission. For streaming, either buffer then authorize whole bundle, or enforce epoch check before each chunk and cancel on change; cannot retract bytes delivered before revocation. Define authorization linearization at final check, acknowledge network race and document revocation latency SLO; no guarantee of retroactively deleting client-held bytes. Cache only authorized payload under scope/grant/cut key and invalidate on policy/identity/revocation/erasure. Audit response under same scope, without raw secrets.

## 11. Security, privacy and threat model (C04, C07, H08)

Threats: curious or malicious developer, compromised agent token, malicious repository/document/tool output, misconfigured RLS, insider admin misuse, stale permission cache, poisoned feedback, model cross-request leakage, resource exhaustion and recovery from old backups. Explicitly distinguish trusted platform operators from untrusted tenant clients; infrastructure-level privileged access requires separate audited controls, not RLS alone.

- API and DB deny by default; test RLS as runtime user, including joins, upserts, bulk/export, background jobs and error paths. Tenant composite FK prevents foreign references even with coincident IDs. No client direct DB/file access under normal product mode; if self-hosted operator has direct access, disclose separate trust boundary and do not claim API permissions constrain superuser.
- Authorize candidate sets before model inference, retrieval context, graph expansions, exports, caches and source excerpts. For ANN shared index, ensure returned candidates and observable metadata cannot expose unauthorized records; separate tenant/security-domain indexes or exact scan when isolation cannot be demonstrated. Apply same to keyword statistics/ranking, alias suggestions and graph degree. No cross-tenant batch content in model context; clear session/KV caches between security domains and restrict telemetry. Model weights/provider are local by default; external egress prohibited unless explicitly owner-approved with data handling review.
- Treat all documents, comments, tool output and generated text as data, never instructions. Delimit/structure untrusted content; model process has no write credentials, shell, connector tools or outbound network; strict typed output, allowlisted IDs and server-side validation. Regex flags are advisory defense-in-depth, not proof of safe text. MCP tool calls enforce original user's scopes and explicit grants server-side; no arbitrary SQL, path or URL fetch from model text. Separate content retrieval from action execution; receiving a memory bundle never authorizes an action. External evidence clearly labelled and omitted from default current answer except explicit evidence request.
- Ingest accepts allowlisted formats/size, bounds decompression/parser recursion, rejects unsupported binaries/archives unless an isolated approved scanner can inspect them. Detect credentials/PII using structured validators, secret scanners and conservative redaction policy; normalize encodings safely, bound regex runtime. Unknown scanner status => reject or ephemeral quarantine (encrypted, access-restricted, short TTL, no indexing/logging); no raw pre-gate event. Never put raw payloads, prompts, vector contents, secrets or auth tokens in telemetry. Redaction output is the durable source; record redaction reason without sensitive value. Detection is imperfect: incident response must handle later discovery and deletion. Test synthetic secrets only, not real credentials.
- Encryption in transit and at rest, scoped service credentials, key rotation, object authorization, secrets manager, dependency pinning, security patch process. Audit every sensitive read/write/decision/recovery with minimal actor, action, scope, outcome, sequence, trace ID. Protect audit against tampering and restrict read permissions. Do not expose personal names/emails in fact payloads; necessary identity metadata has separate retention and access. Security incident blocks unsafe paths, revokes credentials, invalidates caches and triggers §17 suppression/erasure where applicable.

## 12. Answer assembly, derived knowledge and receipts (H04, H08, M09)

Default agent bundle is structured and deterministic after replay; human synthesis is optional and strictly grounded. A synthesis cannot add/upgrade authority or hide uncertainty; all factual claims require authorized source spans, typed evidence validation where possible, otherwise mark inference or omit. Distinguish actual observation from proposed decision. If unsupported synthesis fails checks, return deterministic bundle without prose. The voice mode may compact history but must keep current status, conflict/pending, scope and critical source evidence. No LLM on authoritative resolver path. Retrieval may still use local encoder/reranker models, so latency measurement includes those.

## 13. Model lifecycle and local execution (H02, H03, M08)

Model manifest pins provider, artifact checksum/version, tokenizer, embedding dimensions, normalization, pooling, preprocessing, runtime/dependency versions, quantization, language, prompt/schema versions, calibration dataset hash, threshold/review band and test results. Separate manifests for classifier, embeddings, reranker and NLI. No implicit latest version. Changing any semantic component requires compatibility check; even equal dimensions do not imply same embedding space. Keep separate vector columns/tables/index generations, build in shadow from authorized sanitized documents, catch up deltas to watermark, compare recall/false merges/latency on held-out and adversarial sets, approve atomic active-generation pointer switch; preserve old compatible generation for bounded rollback. Never combine raw distances from incompatible spaces. Record active manifest in each result/filing decision. In-flight query uses pinned generation; restart on authorization changes. If new model is unavailable or uncertain, use deterministic filing/pending and eligible retrieval fallback, not automatic alternate provider. Local deployment hardware and exact models are owner decisions after measurement; V2 did not supply benchmark hardware. ## 14. Team coordination and approvals (C09, M03, M05)

Engineering scopes: restricted developer workspace (engineering only), project/team, approved organization-wide. Upward promotion is a new reviewed assertion in destination scope with explicitly approved sanitized evidence excerpt; source grant is checked for proposer and reviewer; original private source is not automatically readable by destination. Publish only destination-authorized citation artifact and record restricted lineage internally. Similar facts across teams may share a visible approved family label but retain independent values, scope and authority. No automatic propagation of org value into local runtime observation; clients may read both if granted. A policy explicitly defines inheritance/override where applicable.

Proposal lifecycle: `draft -> submitted -> under_review -> approved/rejected/expired/stale -> applied` (or `failed` with reason); votes attach immutable version/digest. Store target IDs, source evidence digest, expected fact/identity/policy/auth versions, before/after preview, impacts, rationale, required roles and expiration. Approval transaction checks current proposer/reviewer permissions, separation of duties, evidence access, exact digest and base preconditions; changed targets or new evidence make it stale; rerun review. Approval and domain transition are atomic for high-risk operations; if async materialization follows, distinguish authoritative applied from projection pending. Duplicate votes idempotent; concurrent approvals serialize. Rejection recorded with rationale; no deletion of audit history.

Stewards are domain roles with primary and backup; queue dedup by issue+target+evidence revision, priority by severity, route only to authorized relevant owner. Proposed operational targets: critical integrity issue triage within one business day, normal review within five business days; owner sets actual staffing/SLA. Unowned domain or overdue critical issue escalates to org admin and stays blocked/uncertain; never auto-approves. Monitor pending age, queue depth, accepted/rejected precision, false negatives sampled, reviewer disagreement and throughput. Deprovision departed contributor, revoke agent credentials, reassign stewards, retain authorized historical decisions under privacy policy. Decision record fields: question, selected claim, alternatives rejected, rationale, decider role/grant, effective/recorded cut, evidence, supersedes link and conflict resolution ID. Organization governance, not raw authority number, decides who can make technical decisions.

## 15. HTTP/MCP contract (M01)

Keep `/v1/ebrain` route family for compatibility; negotiate an explicit schema revision (`schema_version: 3`) and do not silently change legacy response semantics. ## 17. Retention, erasure, backups and recovery (C07, C10)

Append-only is a logical engineering history rule, not unconditional retention of prohibited information. Owner/legal/security review defines data-class retention, jurisdiction/data residency, incident handling and authorized erasure scope before production. Source content, identity mappings, receipts, security audit and backups have distinct retention classes. Never promise legal compliance from this architecture alone. On discovered credential/PII: disable serving affected payload immediately; revoke/rotate exposed credential outside memory as appropriate; record minimal incident ID and payload references without secret; authorized erasure workflow removes/redacts payload across primary, object versions, projection, search index, embeddings, cache, logs/exports under control, worker queues and model caches. Use envelope encryption and sufficiently granular keys if cryptographic erasure is the chosen strategy; verify all copies/key replicas and document limitations of immutable backup retention. Retain non-sensitive structural erasure marker, not recoverable secret or a low-entropy reversible digest. Dependent claims become unsupported/pending unless independently justified. Historical queries cannot reveal erased bytes. Client-held exports cannot be retroactively guaranteed deleted; disclose this. Backup retention expiry/suppression and incident verification are mandatory.

Backups: consistent encrypted Postgres base backup + WAL/PITR, sanitized object snapshots, identity/decision/policy/grant ledger, key and suppression metadata and index manifests. Vector indexes are rebuildable; may back them up for RTO, but a vector-only backup is never sufficient. Record coordinated checkpoint, object manifest and verification checksums. Store suppression/revocation authority in independently recoverable durable control plane so restoring an older snapshot cannot resurrect erased content or stale access. Recovery in isolated environment: restore DB/object manifests, apply latest suppression/revocations and recovery policy, replay WAL/accepted events to target, reconcile counts/digests, rebuild projections/indexes, verify RLS and no erased content, then fence old writer and open traffic only after approved cutover. If latest suppression state cannot be verified, fail closed. Proposed initial SLO targets (owner approval and drill required): RPO <= 5 minutes for disaster scenario, RTO <= 4 hours; normal committed writes must not be silently lost. Acknowledged-write loss after disaster within configured RPO is a serious incident and must be reconciled, not hidden. Run restore drills before launch and quarterly thereafter; report actual RPO/RTO and recovery gaps. Do not claim zero-loss regional DR without measured synchronous replication and failure-domain design.

## 24. Integrated acceptance scenarios (worked examples)

### A. Silent alias update with near-miss

An authorized service owner writes access-token TTL 60m for web/prod at seq 10. Refresh TTL 7d is separate. Later, a verified structured source emits access-token lifetime 45m, revision 2, then 30m, revision 3, without explicit supersedes. Approved alias and full qualified key identify the same fact; source contract orders revisions, server records explicit lineage. Query "web prod auth token TTL" returns 30m only as current; history 60/45 separate; refresh remains distinct. If revision 3 instead arrives as ambiguous free text with no qualifier/source ordering, store safe pending, fence possible access-token fact, ask steward; do not claim 45m current until resolved. This intentionally trades immediate answer coverage for correctness under missing evidence.

### B. Concurrent decision and lower-authority poisoning

Human domain owner and another equally authorized delegate observe 30m, propose 15m and 20m concurrently, same base. First accepted decision alone can be current at its cut; second verified competing branch creates conflict at next cut. A low-authority agent submits `supersedes` and 5m with malicious text: rejected/noncurrent evidence only, no extra conflict from ineligible writer. Reviewed decision chooses 20m with rationale, alternative 15m rejected. Resolver returns only 20m after approval, historical query before conflict still returns earlier state. No timestamp tie-break.

### C. Security, late observation and recovery

Project A approves prod intended TTL 30m; deployment connector observes 60m on Monday but reports Wednesday. On Tuesday as-known query cannot see Wednesday evidence; current as-of-valid Monday with latest knowledge can show observed 60m and intended 30m separately. Project B's agent has no grants to A; cannot discover via exact code, vector, graph, counts, receipts or synthesis. A contributor is revoked, then old backup restored; recovery applies latest revocations/erasure before serving. Historical decision remains for authorized A readers; revoked contributor gets no access.

### D. Worker crash and bad merge

Authorized new assertion commits, worker dies before embedding update. Query on primary with receipt min_seq sees authoritative replay or pending, never stale head from card. An erroneous merge proposal is approved in a test fixture; independent identity audit discovers false equivalence, rebuild alone may not. Safety fence suppresses unsafe current, steward approves split with original bindings, materializer rebuilds and new query resolves both distinct facts. Historical query at earlier knowledge cut reflects then-known mapping unless access/erasure prevents it. Review and evidence preserve why correction occurred.
